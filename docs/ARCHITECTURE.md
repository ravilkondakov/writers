# Архитектура

## Главная идея: модульный монолит + события

Одно Django-приложение, внутри которого чётко разделены модули (`authors`, `stories`, `reviews`,
`events`). Модули не лезут в таблицы друг друга напрямую там, где можно обойтись сервисной
функцией или событием. Тяжёлую и медленную работу выносим из HTTP-запроса.

Почему не микросервисы сразу: пока на платформе нет авторов, микросервисы дают сложность без
выгоды. Модульный монолит с хорошими границами можно потом разрезать по границам модулей.

## Поток данных

```
Клиент ──HTTP──▶ web (Django/DRF, без состояния) ──▶ PostgreSQL
                    │        │
                    │        └─▶ Redis (кэш, результаты задач)
                    │
                    ├─ after commit ─▶ RabbitMQ ─▶ worker (Celery): уведомления, e-mail, тяжёлые задачи
                    │
                    └─ after commit ─▶ Kafka (story.viewed, story.published)
                                          └─▶ consumer: счётчики просмотров, позже рекомендации, аналитика
```

## Что за что отвечает

| Компонент | Зачем | Масштабирование |
|---|---|---|
| web | HTTP API | любое число контейнеров за балансировщиком; состояния нет |
| PostgreSQL | источник истины | индексы, затем реплики на чтение, затем партиционирование |
| Redis | кэш горячих списков, результаты задач | кэш-aside с TTL |
| RabbitMQ + Celery | **задачи**: «сделай это за меня и повтори при сбое» | больше воркеров, отдельные очереди |
| Kafka | **события**: «вот что произошло» (журнал, который читают несколько потребителей) | больше партиций и consumer в одной группе |

**RabbitMQ или Kafka?** RabbitMQ: сообщение адресовано одному исполнителю и после обработки удаляется.
Kafka: событие хранится как запись в журнале, его могут прочитать несколько независимых потребителей
и перечитать позже. Здесь они решают разные задачи, поэтому оба нужны.

## Решения, которые уже заложены

1. **Stateless web**: конфигурация из переменных окружения, сессии и кэш не в памяти процесса.
2. **`transaction.on_commit`**: задача и событие уходят только после успешного коммита.
3. **Читающие запросы в `selectors.py`**: их можно оптимизировать и кэшировать независимо от HTTP.
4. **Конверт события с `event_id`**: основа идемпотентности потребителей.
5. **`acks_late` и `prefetch=1`** в Celery: задача не теряется при падении воркера.

## Известные слабые места (и что с ними делать позже)

- Событие теряется, если Kafka недоступна в момент отправки. Решение: transactional outbox.
- Счётчик просмотров в consumer пока обновляет БД по одному событию. Решение: пачки и/или Redis-счётчик с периодическим сбросом.
- Нет наблюдаемости: метрики (Prometheus), централизованные логи, алерты.
- Одна БД на всё. Это нормально до тех пор, пока нагрузка не доказала обратное.
